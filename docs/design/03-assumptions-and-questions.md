## 1. 명시적 가정 (별도 지시가 없으면 이대로 진행)

| # | 가정 | 영향 범위 |
|---|---|---|
| A1 | DB는 PostgreSQL **16** 이상 (`UNIQUE NULLS NOT DISTINCT` 사용) | 2단계 스키마 |
| A2 | 모든 시각은 `timestamptz`(UTC 저장)로 저장하고, 화면 표시는 리그 `timezone` 기준. 기본 표시 타임존은 `Asia/Seoul` | 전 단계 |
| A3 | raw 원문은 초기에는 PostgreSQL `bytea`(zstd 압축)에 저장. 용량이 커지면 MinIO(S3 호환)로 이전할 수 있도록 `object_key` 컬럼을 미리 둔다 | 2·3단계 |
| A4 | 인증은 **이메일 + 비밀번호**(argon2 해시) + JWT(httpOnly 쿠키). 이메일 인증/비밀번호 재설정 메일은 SMTP 설정 시 활성화 | 5단계 |
| A5 | "팀 공유"의 팀 = 분석가 조직(`workspace`). 스포츠 팀과 구분 | 2·5단계 |
| A6 | 자동 수집 데이터 정정은 **소스 재수집으로만** 반영. 분석가가 "이 기록이 틀렸다"고 표시하는 기능이 필요하면 `analyst` 쪽 메모(태그/코멘트)로 남긴다 | 5·6단계 |
| A7 | 선수 동일인 판별(이적·리그 이동)은 소스별 외부 ID 매핑이 기본이고, 서로 다른 소스 간 동일인 병합은 관리자 수동 확정 | 3·4단계 |
| A8 | 커스텀 지표 수식은 기존 지표(수집·파생)와 리그 상수만 참조 가능. 다른 커스텀 지표 참조는 같은 워크스페이스 내에서만 허용 | 7단계 |
| A9 | 과거 데이터 백필(backfill)은 기본 **최근 3시즌**. 수집 소스가 허용하는 범위 내에서만 | 3·4단계 |
| A10 | xG, 트래킹 데이터처럼 소스가 제공하지 않는 지표는 **계산해서 만들지 않는다**(xG 모델 자체 구축 X). 제공 시에만 수집 | 4단계 |
| A11 | 지표 코드는 영문 대문자 + 카테고리 접두어(`bat.`, `pit.`, `fld.`) 규칙. 커스텀 지표는 `cm.` 접두어 | 2단계 시드 |
| A12 | 데이터 규모 가정: 종목당 1~2개 리그, 리그당 연 수백~2,500경기. 단일 PostgreSQL 인스턴스로 충분 | 성능 설계 |

## 2. ❓ 확인이 필요한 사항

### Q1. 종목별 대상 리그 (가장 중요)
초기 지원할 **구체적인 리그**를 알려주세요. 수집 소스·지표 제공 범위·이용약관이 리그마다 완전히 다릅니다.

| 종목 | 후보 예시 (결정 필요) |
|---|---|
| 야구 | KBO / MLB / NPB |
| 농구 | KBL / WKBL / NBA |
| 배구 | V-리그(남/여) |
| 축구 | K리그1·2 / 해외 리그 |

### Q2. 사용 목적과 소스 이용약관
- 서비스가 **내부 분석용(비공개)**인가요, **외부 공개/상업 서비스**인가요?
- 다수의 공식 리그 사이트·기록 사이트는 약관에서 자동 수집이나 상업적 재배포를 제한합니다.
  3단계에서 각 소스의 robots.txt와 약관을 확인해 `ingest.data_source.terms_note`에 기록하고, **허용되지 않는 소스는 수집기를 만들지 않고 보고**할 예정입니다.
- 공식 데이터 라이선스(유료 API 등)를 이미 보유하고 있다면 알려주세요 — 스크래핑보다 우선합니다.

### Q3. 3단계 첫 번째 수집기 대상
"첫 번째 종목 수집기 1개"를 어느 종목·리그로 할지 정해주세요. (Q1 답변 기준, 데이터 구조가 가장 복잡한 야구로 먼저 검증하는 것을 권장합니다 — 이벤트 로그·투타 스플릿까지 다루면 나머지 종목에서 인터페이스가 부족할 가능성이 줄어듭니다.)

### Q4. 이벤트 로그 수준
플레이 바이 플레이를 어느 깊이까지 원하시나요?
- (a) 득점·교체·카드 등 **주요 이벤트만**
- (b) 야구 **타석 단위**, 농구 **포제션/슛 단위** (좌/우 투수 스플릿에는 최소 타석 단위 필요)
- (c) 야구 **투구 단위**까지 (소스가 제공하는 경우)

### Q5. 운영 환경
- 배포 대상(단일 VM / 클라우드 관리형 DB 사용 여부)
- 알림 채널: Slack Webhook, 이메일 중 사용할 것 (둘 다 가능)

### Q6. 사용자/조직 구조
- 한 설치본을 **여러 조직**(구단 A, 매체 B)이 같이 쓰나요, **한 조직 전용**인가요? → 워크스페이스 격리 수준(RLS 필수 여부)이 달라집니다.

## 3. 다음 단계(2단계) 예정 산출물

1단계 승인 시 아래를 진행합니다.

1. `backend/migrations/` — Alembic 기반 SQL 마이그레이션 (스키마 `config`/`core`/`ingest`/`analyst`/`auth`, 권한 계정 `app_api`/`app_ingest`/`app_readonly`, 변경 이력 트리거, RLS 정책, 롱포맷 MV)
2. `config/sports/{baseball,basketball,volleyball,football}.yaml` — 구간·포지션·이벤트 타입·지표 정의(원시+파생 수식)·스플릿·자격 조건 시드
3. `sync-config` CLI — YAML → config 테이블 upsert (수식 순환 참조·미정의 지표 참조 검증 포함)
4. `docker-compose.yml`의 `db` 서비스 + 마이그레이션 적용 스모크 테스트
